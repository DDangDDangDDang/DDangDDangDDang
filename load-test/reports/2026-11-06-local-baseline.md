# 부하 테스트 결과: 로컬 기준선 (2026-11-06)

처음으로 숫자를 올려 가며 측정한 결과다. 목적은 **어디가 먼저 막히는지** 찾는 것이고, 절대 수치는 운영에 그대로 옮길 수 없다(맨 아래 "한계" 참고).

## 환경

| 항목 | 값 |
| --- | --- |
| PC | 12코어, 메모리 16GB, Windows 11 |
| 서버 | `loadtest` 프로필, 8090, 별도 DB `ddang_loadtest`(로컬 MySQL), Redis 1번 DB(Docker) |
| 설정 | HikariCP 최대 10개, Tomcat 스레드 200·대기열(`accept-count`) 100 (모두 Spring Boot 기본값) |
| 부하 도구 | k6 v2.3.0, **서버와 같은 PC**에서 실행 |
| 지표 | Prometheus + Grafana (`load-test/monitoring`) |

## 1. 입찰: 한 경매에 입찰이 몰릴 때

시나리오 `bid.js`(MODE=hot): 회원 200명이 경매 하나를 조회한 뒤 최소 입찰가로 입찰한다. 단계마다 10초 동안 올리고 60초 유지했다. **오전(10:10~10:18)에 한 번씩 잰 값**이다. 같은 조건을 오후에 다시 잰 결과는 4장에 있다.

| 초당 입찰 시도 | 50 | 100 | 200 | 400 | **800** |
| --- | ---: | ---: | ---: | ---: | ---: |
| 입찰 p95 (k6) | 30ms | 27ms | 63ms | 69ms | **268ms** |
| 입찰 최대 | 221ms | 89ms | 103ms | 118ms | **866ms** |
| 경매 상세(GET) p95 (서버) | 10ms | 8ms | 7ms | 9ms | **208ms** |
| 실패율 (5xx·연결 실패) | 0% | 0% | 0% | 0% | **6.5%** |
| `AUCTION_018` (락 재시도 포기) | 0 | 0 | 0 | 0 | 0 |
| 현재가 정합성 | OK | OK | OK | OK | OK |
| 커넥션 풀 사용 최대 (10개 중) | 2 | 3 | 4 | 9 | **10** |
| 커넥션 대기 요청 최대 | 0 | 0 | 0 | 0 | **180** |
| 커넥션 얻는 시간 최대 | 1ms | 1ms | 4ms | 50ms | **707ms** |
| 커넥션 쥔 시간 평균 | 3.1ms | 2.5ms | 2.5ms | 2.8ms | 3.9ms |
| Tomcat 일하는 스레드 최대 (200개 중) | 3 | 4 | 10 | 20 | **199** |
| 서버 CPU 평균 | 8% | 11% | 19% | 33% | 43% |
| PC 전체 CPU 평균 | 64% | 58% | 68% | 91% | **100%** |

### 읽는 법

- **오전 측정에서는 초당 400건까지 실패 0, p95 69ms, 정합성 OK**였다. 락 재시도 포기(`AUCTION_018`)와 BLOCKED 스레드도 한 번도 없었다.
  - 다만 400 단계에서 이미 커넥션 풀 10개 중 9개를 썼다.
  - 4장에서 같은 조건(풀 10, 400건)을 오후에 두 번 다시 재 보니 p95 167·193ms, 실패 0.2%였다. 오전 결과는 재현되지 않았다.
  - 그래서 **400건은 "안정적인 범위"가 아니라, 풀이 차기 시작해 PC 상태에 따라 결과가 흔들리는 경계**로 본다.
  - 정합성과 `AUCTION_018` 0건은 모든 측정에서 같았다. 비관적 락 + 재시도 설계 자체는 이 범위에서 잘 버틴다.
- **800건에서 가장 먼저 꽉 찬 것은 DB 커넥션 풀**이다.
  - 커넥션 10개가 모두 쓰였고, 최대 180개 요청이 커넥션을 기다렸다(커넥션을 얻는 데 최대 0.7초).
  - 기다리는 요청이 Tomcat 스레드를 붙잡고 있어서, 스레드 200개도 거의 다 찼다(199개).
  - 그 결과 **입찰과 상관없는 조회(경매 상세)까지 p95가 9ms → 208ms로 느려졌다.** 커넥션 풀은 모든 API가 함께 쓰기 때문이다.
  - 그래도 커넥션 하나를 쥐는 시간은 평균 3~4ms로 짧다. 트랜잭션이 느린 게 아니라 **동시에 들어오는 양이 풀 크기를 넘은 것**이다.
- **800건의 실패 6.5%는 거의 모두 "연결 거부"**다(k6 로그에서 `connection refused` 6,278건, 클라이언트 포트 재사용 오류 2건). **원인은 확정하지 못했다.**
  - Tomcat(NIO)은 작업 스레드가 모두 바빠도 `max-connections`(기본 8192)까지 연결을 받아 둔다. k6 연결은 VU 200개 안팎이고 keep-alive로 다시 쓴다. 그래서 "스레드가 바빠서 `accept-count`(100) 대기열이 넘쳤다"고 보기는 어렵다.
  - 후보는 다음과 같다. 어느 것인지는 설정을 바꿔 다시 재야 한다(아래 "다음에 해 볼 것" 2번).
    - PC CPU가 100%라 연결을 받는 스레드(acceptor)가 밀렸다.
    - Tomcat이 연결 하나당 요청 100개(`max-keep-alive-requests` 기본값) 뒤에 연결을 닫아, k6의 재연결이 몰렸다.
    - Windows에서 클라이언트 쪽 포트·TIME_WAIT 문제가 생겼다.
- **입찰 성공률(초당 약 35~50건)이 시도가 늘어도 오르지 않는 것은 서버 한계가 아니다.** 시나리오 특성이다. 모두가 "방금 본 최소 입찰가"로 입찰하므로, 한 명이 성공하면 같은 가격으로 들어온 나머지는 `AUCTION_016`(최소가 미달)으로 진다. 서버는 이 패배 응답까지 포함해 초당 약 365건(400 단계)을 정상 처리했다.

### 800 단계의 주의점

- k6 VU가 200개 상한에 걸려 3,195건은 아예 보내지 못했다(`dropped_iterations`). 시드 회원 수(200명)가 VU 상한이다.
- PC 전체 CPU가 100%였다. k6와 서버가 CPU를 나눠 쓰고 있어, 800 단계의 지연 일부는 PC 자체가 바빠서 생겼을 수 있다.
- 그래도 "커넥션 풀이 먼저 막힌다"는 순서는 서버 지표로 분명히 보인다.

## 2. 채팅: 한 방송에 시청자가 몰릴 때

시나리오 `chat.js`: 접속자의 10%가 3초마다 말하고, 60초 유지했다.

| 접속자 | 100 (동시 접속) | 500 (동시 접속) | 1000 (동시 접속) | **1000 (10초에 걸쳐 접속)** |
| --- | ---: | ---: | ---: | ---: |
| 연결 성공 | 100% | **59%** | **37%** | **100%** |
| 연결 거부 | 0 | 다수 | 다수 | 0 |
| 보낸 메시지 | 190 | 758 | 1,342 | 1,892 |
| 받은 메시지 / 기대값 | 19,000 / 19,000 | 222,094 / 293명분 일치 | 501,000 / 374명분 거의 일치 | 1,807,497 (95.5%)* |
| 전달 지연 p95 | 14ms | 24ms | 87ms | **257ms** |
| 전달 지연 최대 | 92ms | 172ms | 405ms | 795ms |
| 서버 CPU 평균 | - | 3% | 6% | 15% |
| PC 전체 CPU 평균 | - | 45% | 66% | 79% |

\* 이 열은 정확히 대조하지 않았다. 각자 접속한 때부터 60초를 머무르므로, 늦게 들어온 사람은 들어오기 전 메시지를 못 받고, 일찍 들어온 사람은 늦게 들어온 송신자의 마지막 메시지를 받기 전에 나간다.
  - 접속 시각이 0~10초에 고르게 흩어지면, 두 사람의 접속 시각 차이는 평균 약 3.3초다.
  - 60초 중 약 5.6%가 겹치지 않으므로, 기대 수신율은 약 94%다. 관측값 95.5%와 크게 어긋나지는 않는다.
  - 그래도 "유실 없음"의 근거로는 쓰지 않는다. 정확히 대조하려면 송신 시작을 접속이 끝난 뒤로 미뤄야 한다.

### 읽는 법

- **동시 접속 단계에서 연결된 사람에게는 메시지가 빠짐없이 전달됐다.** 500명 단계는 연결된 293명 × 758건 = 222,094건으로 정확히 일치했다. (흩어 접속한 열은 위 각주대로 정확한 대조를 하지 않았다)
- **500명 이상이 같은 순간에 접속하면 연결 일부가 거부됐다.**
  - 접속을 10초에 걸쳐 흩자 1000명이 모두 연결됐다. 그래서 수용 인원 문제가 아니라 **동시 접속 몰림(burst)** 문제다.
  - 짧은 순간에 연결 수백 개가 한꺼번에 쏟아지는 경우라, OS의 연결 대기열(listen backlog, Tomcat `accept-count` 100)이 순간적으로 넘친 것으로 **추정**한다. `accept-count`를 바꿔 다시 재 보지는 않았다.
  - 실제로는 방송 시작 알림을 받은 시청자가 한꺼번에 들어올 때 생길 수 있다. 운영은 Caddy가 앞에서 연결을 받으므로 양상이 다를 수 있다.
- **전달 지연은 메시지 퍼뜨리는 양에 따라 늘었다**(1000명 × 초당 약 33건 = 초당 약 3만 건 전달일 때 p95 257ms).
  - 하지만 이때 서버 CPU는 15%였고, PC 전체는 79%였다. **CPU 대부분을 k6가 수신 처리에 썼다.**
  - 그래서 이 지연이 서버 한계인지 k6 한계인지 이 PC로는 가릴 수 없다.

## 4. 실험: 커넥션 풀을 키우면 나아지나

1장에서 커넥션 풀이 먼저 꽉 찼으므로 `SPRING_DATASOURCE_HIKARI_MAXIMUMPOOLSIZE`를 10 / 20 / 30으로 바꿔 입찰을 다시 쟀다(같은 시나리오, 10초 램프 + 60초 유지).

### 첫 비교: 오히려 나빠진 것처럼 보였다

| 초당 400건 | 풀 10 (오전) | 풀 20 | 풀 30 |
| --- | ---: | ---: | ---: |
| 입찰 p95 | 69ms | 155ms | 136ms |
| 커넥션 쥔 시간 평균 | 2.8ms | 6.7ms | 7.0ms |

풀 10은 오전에 쟀고, 풀 20·30은 오후에 쟀다. 그래서 **같은 오후 시간대에 풀 10을 다시 재 보니 p95가 167ms로, 오전 결과(69ms)가 재현되지 않았다.** 시간대가 다르면 PC의 다른 작업량(브라우저 등)이 달라, 그 차이가 풀 크기의 효과보다 컸던 것이다.

→ 그래서 **풀 10과 30을 번갈아 두 번씩** 재고, 그동안 MySQL 행 락 대기(`Innodb_row_lock_waits`, `Innodb_row_lock_time`)가 얼마나 늘었는지도 함께 쟀다.

### 번갈아 잰 결과 (초당 400건, 오후)

| | 풀 10 (1차) | 풀 10 (2차) | 풀 30 (1차) | 풀 30 (2차) |
| --- | ---: | ---: | ---: | ---: |
| 입찰 p95 | 167ms | 193ms | **108ms** | **133ms** |
| 실패율 (연결 거부) | 0.21% | 0.25% | **0%** | **0.01%** |
| 못 보낸 요청 (k6 VU 부족) | 84 | 125 | 0 | 0 |
| DB 행 락 대기 횟수 | 5,094 | 4,718 | 7,582 | 6,565 |
| DB 행 락 대기 시간 합계 | 30.1초 | 27.7초 | **55.4초** | **54.4초** |

### 읽는 법

- **같은 조건에서 비교하면 풀 30이 조금 낫다.** 입찰 p95가 약 180ms에서 약 120ms로 줄었고, 연결 거부도 거의 사라졌다.
- **대신 DB 안에서 락을 기다리는 시간이 약 2배가 됐다**(약 29초 → 약 55초).
  - 입찰은 모두 같은 경매 행을 잠그므로 한 번에 하나씩만 처리된다.
  - 커넥션을 늘려도 이 줄은 빨라지지 않는다. **기다리는 장소가 앱의 커넥션 풀에서 DB의 락 대기로 옮겨 갈 뿐이다.**
  - 앱에서 기다리는 시간이 줄어 Tomcat 스레드와 다른 API는 덜 막히므로, 응답 시간은 조금 좋아졌다.
- **초당 800건에서는 풀 20·30도 실패했다**(실패율 12~14%, 대부분 연결 거부). 한 경매에 초당 800건이 몰리는 상황은 풀 크기로 해결되지 않는다.

### 이 실험에서 배운 것

1. **비교는 같은 조건에서, 여러 번 번갈아 재야 한다.** 한 번씩만 쟀다면 "풀을 키우면 나빠진다"는 틀린 결론을 냈을 것이다.
2. **자원을 늘렸을 때 병목이 어디로 옮겨 가는지** 같이 봐야 한다. 이번에는 앱의 커넥션 대기 → DB 락 대기로 옮겨 갔다.
3. 운영에 풀 크기를 바로 바꾸지는 않는다.
   - 운영 DB(RDS)의 최대 연결 수와 서버 대수를 함께 따져야 한다.
   - 이 효과가 운영 사양(2 vCPU)에서도 나타나는지 확인이 먼저다.

## 정리: 먼저 막히는 곳

1. **DB 커넥션 풀 (HikariCP 10개)**: 입찰이 초당 400건 부근에서 차기 시작하고(오전 9/10 사용, 오후에는 p95 약 180ms에 실패 0.2%), 800건에서는 확실히 꽉 찬다. 차면 입찰과 상관없는 조회까지 함께 느려진다.
2. **연결 거부 (원인 미확정)**: 입찰 800건과 채팅 동시 접속 500명 이상에서 `connection refused`가 났다. 채팅은 연결 대기열(`accept-count` 100)이 순간적으로 넘친 것으로 추정한다. 입찰은 연결 수가 적어 다른 원인일 수 있다.
3. 락, 트랜잭션 길이, GC, 메모리는 이번 범위에서 문제가 없었다(GC 멈춤 0.4% 이하, 힙 최대 약 530MB).

## 한계 (이 숫자를 믿으면 안 되는 이유)

- **k6와 서버가 같은 PC**에서 돌아 CPU를 나눠 썼다. 입찰 800 단계와 채팅 1000명 단계는 PC 전체 CPU가 80~100%였다.
- **운영과 구성이 다르다.**
  - 운영: EC2 t3.small(2 vCPU, 메모리 2GB) + RDS + ElastiCache, 앞단에 Caddy
  - 로컬: 12코어 PC, DB가 같은 PC
  - 운영 서버는 CPU가 훨씬 적고 DB까지 네트워크 왕복이 있어, 한계가 더 낮게 나올 가능성이 크다.
- 테스트 데이터가 적어 목록·검색 쿼리 성능은 확인되지 않았다.
